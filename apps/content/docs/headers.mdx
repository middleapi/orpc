---
title: "Headers"
description: "Read request headers and set response headers from procedures, middleware, interceptors, plugins, and clients through the built-in headers in oRPC context."
---

Handlers and links inject the request and response headers into the [context](/docs/context), as `Headers` instances. Read them with `getRequestHeaders` and `getResponseHeaders` wherever the context is available, such as in middleware, procedures, interceptors, and plugins. No plugin is needed.

## Server

```ts twoslash
import { getRequestHeaders, getResponseHeaders, os } from '@orpc/server'
import { getCookie, setCookie } from '@orpc/server/helpers'

const procedure = os
  .use(({ context, next }) => {
    const sessionId = getCookie(getRequestHeaders(context), 'session_id')
    getResponseHeaders(context)?.set('x-request-id', crypto.randomUUID())

    return next()
  })
  .handler(({ context }) => {
    const userAgent = getRequestHeaders(context)?.get('user-agent')

    setCookie(getResponseHeaders(context), 'session_id', 'abc123', {
      secure: true,
      maxAge: 3600,
    })

    return { userAgent }
  })
```

Once a handler matches a procedure, and before its [interceptors](/docs/rpc/handler#interceptors) run, it injects:

- **Request headers**: a copy of the headers of the request, or of the subrequest in a [batch](/docs/plugins/batch).
- **Response headers**: empty at first, then merged into the response, error responses included. Duplicate names keep both values.

[Routing interceptors](/docs/rpc/handler#routing-interceptors) run before matching, so they use the headers of `request` and of the returned response instead.

:::info[Why can the headers be `undefined`?]
Only handlers and links inject them. In [server-side calls](/docs/client/server-side), they are `undefined` unless you [provide them](#providing-headers).
:::

:::tip
Combine with [Cookie Helpers](/docs/helpers/cookie), which accept `undefined` headers, for streamlined cookie management.
:::

### Providing Headers

Provide the headers in the initial context under `REQUEST_HEADERS_CONTEXT_SYMBOL` and `RESPONSE_HEADERS_CONTEXT_SYMBOL`, for example to forward the headers of your framework in [server-side calls](/docs/client/server-side):

```ts twoslash
import { call, getResponseHeaders, os, REQUEST_HEADERS_CONTEXT_SYMBOL, RESPONSE_HEADERS_CONTEXT_SYMBOL } from '@orpc/server'

declare const request: Request

const procedure = os.handler(({ context }) => {
  getResponseHeaders(context)?.set('cache-control', 'no-store')
})
// ---cut---
const responseHeaders = new Headers()

await call(procedure, undefined, {
  context: {
    [REQUEST_HEADERS_CONTEXT_SYMBOL]: request.headers,
    [RESPONSE_HEADERS_CONTEXT_SYMBOL]: responseHeaders,
  },
})

console.log(responseHeaders.get('cache-control')) // 'no-store'
```

Handlers ignore the headers in their initial context: they take the request headers from the request, and start the response headers empty.

## Client

Links inject the headers before their [interceptors](/docs/rpc/link#interceptors) run:

- **Request headers**: their headers are merged into the request, after the link's [`headers` option](/docs/rpc/link#url-and-header-options). Duplicate names keep both values.
- **Response headers**: filled with the headers of the response, replacing those of an earlier attempt, such as a [retried](/docs/plugins/retry) one.

Provide them in the client context to set request headers and read response headers per call:

```ts twoslash
import type { RouterClient } from '@orpc/server'
import { os } from '@orpc/server'

const router = { planet: { find: os.handler(() => ({ name: 'Earth' })) } }

declare const client: RouterClient<typeof router>
// ---cut---
import { REQUEST_HEADERS_CONTEXT_SYMBOL, RESPONSE_HEADERS_CONTEXT_SYMBOL } from '@orpc/client'

const responseHeaders = new Headers()

const planet = await client.planet.find(undefined, {
  context: {
    [REQUEST_HEADERS_CONTEXT_SYMBOL]: new Headers({ 'x-tenant-id': 'acme' }),
    [RESPONSE_HEADERS_CONTEXT_SYMBOL]: responseHeaders,
  },
})

const remaining = responseHeaders.get('x-ratelimit-remaining')
```

The link copies the request headers you provide, so changes made during the call never reach your instance, and fills the response headers you provide. Each call keeps its own headers, even when the [Batch Plugin](/docs/plugins/batch) sends it with others.

If you type your [client context](/docs/client/client-side#client-context), extend `HeadersContext` to accept these keys:

```ts twoslash
import type { HeadersContext } from '@orpc/client'

interface ClientContext extends HeadersContext {
  token?: string
}
```

Link interceptors and plugins use the same helpers:

```ts twoslash
import { getRequestHeaders, getResponseHeaders } from '@orpc/client'
import { RPCLink } from '@orpc/client/fetch'
// ---cut---
const link = new RPCLink({
  origin: 'http://localhost:3000',
  url: '/rpc',
  interceptors: [
    async ({ context, next }) => {
      getRequestHeaders(context)?.set('x-request-id', crypto.randomUUID())

      const output = await next()

      console.log(getResponseHeaders(context)?.get('x-request-id'))

      return output
    },
  ],
})
```

:::warning
Browsers hide most headers of cross-origin responses from JavaScript, and `set-cookie` from any response. To read others, list them in the `exposeHeaders` option of the [CORS Plugin](/docs/plugins/cors).
:::
