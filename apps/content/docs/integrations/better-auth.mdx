:::warning
This guide assumes familiarity with [Better Auth](https://better-auth.com/). Review the official documentation if needed.
:::

The integration resolves the Better Auth session in middleware, with its type inferred from your auth instance. It also forwards the cookies Better Auth sets while reading the session, such as a refreshed session cookie or the [cookie cache](https://better-auth.com/docs/concepts/session-management#cookie-cache), and looks the session up once per HTTP request, even across a [batch](/docs/plugins/batch).

## Installation

```package-install
npm install @orpc/better-auth@beta better-auth
```

## Setup

Add `BetterAuthHandlerPlugin` to your handler. It gives the session middlewares access to the request headers and applies the cookies they collect to the response. It does not take your auth instance; the middlewares do.

```ts
import { BetterAuthHandlerPlugin } from '@orpc/better-auth'

const handler = new RPCHandler(router, {
  plugins: [
    new BetterAuthHandlerPlugin(),
  ],
})
```

:::info
The `handler` can be any supported oRPC handler, such as [RPCHandler](/docs/rpc/handler), [OpenAPIHandler](/docs/openapi/handler), or a custom one.
:::

Mount Better Auth's own routes next to oRPC as usual; `auth.handler` is a plain `(request: Request) => Promise<Response>`.

## Protected Procedures

`requireSession` adds the session to the context, or throws an `UNAUTHORIZED` error when the request has none. `optionalSession` adds the session, or `null`:

```ts
import { optionalSession, requireSession } from '@orpc/better-auth'
import { os } from '@orpc/server'
import { auth } from './auth'

const router = {
  me: os
    .use(requireSession({ auth }))
    .handler(({ context }) => context.session.user),

  greeting: os
    .use(optionalSession({ auth }))
    .handler(({ context }) => `Hello, ${context.session?.user.name ?? 'guest'}`),
}
```

`context.session` is `typeof auth.$Infer.Session`, so fields added by plugins or `additionalFields` are typed too. Only a missing session becomes `UNAUTHORIZED`; other errors from `getSession` propagate to oRPC's [error handling](/docs/error-handling).

`auth` also accepts a function, optionally async, that receives the middleware options and input. Use it when the instance lives in the context, for example with dependency injection or one instance per tenant:

```ts
const procedure = os
  .$context<{ auth: typeof auth }>()
  .use(requireSession({ auth: ({ context }, input) => context.auth }))
```

:::info
Lookups are deduplicated by instance identity: within one HTTP request, every middleware that resolves to the same instance shares one `getSession` call. A function that creates a new instance on every call opts out of this.
:::

The lookup only runs when a procedure uses one of the middlewares, so public procedures cost nothing.

## Server-Side Calls

Without the plugin, for example in [server-side calls](/docs/client/server-side), tests, or a custom entrypoint, pass the request headers with `createBetterAuthContext`:

```ts
import { createBetterAuthContext } from '@orpc/better-auth'
import { call } from '@orpc/server'

const user = await call(router.me, undefined, {
  context: createBetterAuthContext({ headers: request.headers }),
})
```

`headers` accepts a `Headers` instance or a plain object such as Node.js `req.headers`. If neither the plugin nor `createBetterAuthContext` provided the headers, the middlewares throw an error describing the missing setup instead of treating the request as signed out.

When the handler receives a context that already contains this state, the plugin reuses it, and still applies the collected cookies to its response.

## Batching

The plugin runs outside the [Batch Plugin](/docs/plugins/batch), so all subrequests of a batch share one session lookup per auth instance. The cookies it collects are applied to the batch response, next to the cookies the batch carries from its subresponses, such as those set through the [Response Headers Plugin](/docs/plugins/response-headers).

## Clients

### Browser

Browsers store and send cookies on their own. For cross-origin requests, include credentials in a custom `fetch`:

```ts
const link = new RPCLink({
  url: 'https://api.example.com/rpc',
  fetch: (url, init) => globalThis.fetch(url, { ...init, credentials: 'include' }),
})
```

The server must allow credentials, for example with the [CORS Plugin](/docs/plugins/cors) and `credentials: true`.

### Expo

[`@better-auth/expo`](https://better-auth.com/docs/integrations/expo) keeps cookies in secure storage instead of a browser cookie jar. Send them with the [Cookies Management Plugin](/docs/plugins/cookies-management):

```ts
import { CookiesManagementLinkPlugin } from '@orpc/client/plugins'
import { authClient } from './auth-client'

const link = new RPCLink({
  url: 'https://api.example.com/rpc',
  plugins: [
    new CookiesManagementLinkPlugin({
      getCookie: () => authClient.getCookie(),
    }),
  ],
})
```

`@better-auth/expo` has no public API to store cookies, so cookies refreshed through oRPC are not saved on the device. The session stays valid on the server, and the Better Auth client stores fresh cookies on its next own request, such as `authClient.getSession()`.

### Server-Side Rendering

A client that runs on the server during SSR has no cookies of its own. Forward the incoming request's `cookie` header:

```ts
const link = new RPCLink({
  url: 'https://api.example.com/rpc',
  plugins: [
    new CookiesManagementLinkPlugin({
      getCookie: () => getIncomingRequest().headers.get('cookie') ?? undefined,
    }),
  ],
})
```

`getIncomingRequest` stands for your framework's way to read the current request, such as `headers()` in Next.js or `getRequestHeaders()` in TanStack Start. When the server and the procedures run in the same process, a [server-side client](/docs/client/server-side) with `createBetterAuthContext` avoids the HTTP round trip.

## NestJS

Register the plugin in `ORPCModule`. NestJS applies the collected cookies to the reply like any other response header. When the auth instance comes from dependency injection, provide it through the [initial context](/docs/integrations/nest#initial-context) and resolve it with the function form of `auth`:

```ts
@Module({
  imports: [
    ORPCModule.forRootAsync({
      useFactory: (auth: AuthService) => ({
        context: { auth: auth.instance },
        plugins: [new BetterAuthHandlerPlugin()],
      }),
      inject: [AuthService],
    }),
  ],
})
export class AppModule {}

const procedure = os
  .$context<{ auth: typeof auth }>()
  .use(requireSession({ auth: ({ context }) => context.auth }))
```

`@orpc/nest` registers one route per procedure and has no batch endpoint, so the batching notes above do not apply.

## Limitations

- The session is resolved with Better Auth's default `getSession` options. Use `auth.api.getSession` in your own middleware if you need `disableCookieCache` or `disableRefresh`.
