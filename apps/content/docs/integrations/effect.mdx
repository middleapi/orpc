## Installation

```package-install
npm install @orpc/experimental-effect@beta effect
```

## Effectful Handlers

`handlerGen` allows you to write effectful handlers using generator functions. Inside the generator, you can yield Effect operations, and `handlerGen` will handle the execution and error handling for you.

```ts twoslash
import { os } from '@orpc/server'
// ---cut---
import { handlerGen } from '@orpc/experimental-effect'
import { Effect } from 'effect'

const procedure = os.handler(handlerGen(function* ({ input, context }) {
  // You can use Effect's features here, such as concurrency, error handling, etc.
  const result = yield* Effect.promise(() => Promise.resolve(5))
  return result
}))
```

### `.effect` extension

Import `@orpc/experimental-effect/extensions/effect` from a module that always runs during initialization, such as the file where you define your base builder or create your server. This adds an `.effect` method to the builder so you can write effectful handlers directly.

<CodeGroup>

```ts usage
const procedure = base.effect(function* ({ input, context }) {
  // You can use Effect's features here, such as concurrency, error handling, etc.
  const result = yield* Effect.promise(() => Promise.resolve(5))
  return result
})
```

```ts setup
import '@orpc/experimental-effect/extensions/effect'

import { os } from '@orpc/server'

export const base = os
```

</CodeGroup>

`.effect` also works when implementing a [contract](/docs/contract/implementation), where the return value is checked against the contract's output schema:

```ts
import '@orpc/experimental-effect/extensions/effect'

import { implement } from '@orpc/server'

const os = implement(contract)

const findPlanet = os.planet.find.effect(function* ({ input }) {
  const planet = yield* Effect.promise(() => db.planet.find(input.id))
  return planet
})
```

### Effect Services

You can provide Effect services through the oRPC context in a typesafe way with `WithEffectContext` and `effect/context`:

```ts twoslash
import { call, os } from '@orpc/server'
// ---cut---
import { handlerGen, WithEffectContext } from '@orpc/experimental-effect'
import { Context, Effect } from 'effect'

class Random extends Context.Service<
  Random,
  {
    readonly next: Effect.Effect<number>
  }
>()('app/Random') {}

interface ServerContext extends WithEffectContext<Random> {}

const procedure = os
  .$context<ServerContext>()
  .handler(handlerGen(function* ({ input, context }) {
    const random = yield* Random
    const result = yield* random.next
    return result
  }))

const random = await call(procedure, undefined, {
  context: {
    'effect/context': Context.empty().pipe(
      Context.add(Random, {
        next: Effect.sync(() => Math.random()),
      }),
    )
  }
})
```

:::info
You can also extend the Effect context with [middleware](/docs/middleware):

```ts
const procedure = os
  .$context<ServerContext>()
  .use(({ context, next }) => {
    return next({
      context: {
        'effect/context': context['effect/context'].pipe(
          Context.add(AdditionService, {}),
        )
      }
    })
  })
  .handler(handlerGen(function* ({ input, context }) {
    const additionService = yield* AdditionService
  }))
```

:::

#### Providing Services with Layers

Services usually come from a [Layer](https://effect.website/docs/requirements-management/layers/). Build your application layer once with a [`ManagedRuntime`](https://effect.website/docs/runtime/#managedruntime) and pass its context to every request. The layer is built on the first `runtime.context()` call, and later calls reuse it:

```ts
import type { WithEffectContext } from '@orpc/experimental-effect'
import { Context, Effect, Layer, ManagedRuntime } from 'effect'

class Database extends Context.Service<Database, {
  query: (sql: string) => Effect.Effect<ReadonlyArray<unknown>>
}>()('app/Database') {
  static readonly layer = Layer.effect(
    Database,
    Effect.gen(function* () {
      const pool = yield* Effect.acquireRelease(
        Effect.sync(() => createPool()),
        pool => Effect.promise(() => pool.end()),
      )

      return Database.of({
        query: Effect.fn('Database.query')(function* (sql) {
          return yield* Effect.promise(() => pool.query(sql))
        }),
      })
    }),
  )
}

interface ServerContext extends WithEffectContext<Database> {}

const runtime = ManagedRuntime.make(Database.layer)

export async function fetch(request: Request) {
  const { matched, response } = await handler.handle(request, {
    context: {
      'effect/context': await runtime.context(),
    },
  })

  if (matched) {
    return response
  }

  return new Response('Not Found', { status: 404 })
}

// Release resources, such as the pool, on shutdown
process.once('SIGTERM', () => {
  void runtime.dispose()
})
```

Combine several layers with `Layer.mergeAll` or `Layer.provideMerge` before creating the runtime. If your app creates more than one `ManagedRuntime`, pass them a shared `memoMap: Layer.makeMemoMapUnsafe()` so layers they have in common are built only once.

:::warning
Don't provide layers inside `effect/wrap`, such as `effect => effect.pipe(Effect.provide(AppLayer))`. The wrap runs for every `middlewareGen` and `handlerGen`, so the layer would be built, and its resources acquired and released, several times per request.
:::

### Error Handling

This integration preserves the original error whenever possible. If you call `Effect.fail(error)`, the error is forwarded to [middleware](/docs/middleware) and interceptors, just like a regular thrown error.

To customize this behavior, wrap the effect before execution using `effect/wrap` in the context:

```ts
import { Context, Effect } from 'effect'

interface ServerContext extends WithEffectContext<never> {}

export async function fetch(request: Request) {
  const { matched, response } = await handler.handle(request, {
    context: {
      'effect/context': Context.empty(),
      'effect/wrap': (effect, opts) => effect.pipe(
        Effect.catchCause((cause) => {

        })
      ),
    }
  })

  if (matched) {
    return response
  }

  return new Response('Not Found', { status: 404 })
}
```

:::info
For app level error handling, we recommend [middleware](/docs/middleware) or interceptors.
:::

### Typesafe Errors

An `ORPCError` that fails the effect, such as `return yield* Effect.fail(new ORPCError(...))`, is thrown from the handler exactly like a thrown `ORPCError` in a regular handler. Define your errors with `.errors` and fail with `errors.X(...)` to make them [typesafe](/docs/error-handling#typesafe-errors) on the client:

```ts
const procedure = os
  .errors({
    NOT_FOUND: {
      message: 'The resource you are looking for does not exist',
    },
  })
  .handler(handlerGen(function* ({ errors }) {
    if (resourceNotFound) {
      return yield* Effect.fail(errors.NOT_FOUND())
    }

    return 'Success'
  }))

const [error, result] = await safe(call(procedure))

if (isDefinedError(error)) {
  // typesafe error handling
}
```

Your services likely fail with their own errors, such as a [Schema.TaggedError](https://effect.website/docs/error-management/yieldable-errors/). Map the ones the client should see to `errors.X(...)` with `Effect.catchTags`, and keep the original as the `cause`:

```ts
import { Context, Effect, Schema } from 'effect'

class UserNotFound extends Schema.TaggedError<UserNotFound>()('UserNotFound', {
  id: Schema.String,
}) {}

class Users extends Context.Service<Users, {
  findById: (id: string) => Effect.Effect<User, UserNotFound>
}>()('app/Users') {}

const findUser = os
  .$context<WithEffectContext<Users>>()
  .errors({
    NOT_FOUND: {
      message: 'User not found',
    },
  })
  .input(Schema.toStandardSchemaV1(Schema.Struct({ id: Schema.String })))
  .handler(handlerGen(function* ({ input, errors }) {
    const users = yield* Users

    return yield* users.findById(input.id).pipe(
      Effect.catchTags({
        UserNotFound: error => Effect.fail(errors.NOT_FOUND({ cause: error })),
      }),
    )
  }))
```

### Catching ORPCErrors

Use `catchORPCError` to recover from every `ORPCError` failure in the error channel of an effect, or `catchORPCErrorCode` and `catchORPCErrorCodes` to recover from specific codes only. Recovered errors are excluded from the resulting effect, and other failures re-fail with their original cause:

```ts
import { catchORPCError, catchORPCErrorCode, catchORPCErrorCodes } from '@orpc/experimental-effect'
import { Effect } from 'effect'

const recovered = program.pipe(
  catchORPCError(error => Effect.succeed(`caught ${error.code}`)),
)

const fallback = program.pipe(
  catchORPCErrorCode('NOT_FOUND', error => Effect.succeed(null)),
)

const handled = program.pipe(
  catchORPCErrorCodes({
    NOT_FOUND: error => Effect.succeed(null),
    CONFLICT: error => Effect.succeed(error.message),
  }),
)
```

`error.data` is typed only when the error channel holds nothing but declared `ORPCError`s. Otherwise, as with [client calls](#client-calls), it is `unknown`.

:::info
All utilities support data-first `catchORPCError(program, handler)` and data-last `program.pipe(catchORPCError(handler))` styles.
:::

### Interruption

When a request is aborted, for example because the client disconnects, oRPC aborts the procedure's `signal`. This interrupts the fibers running your `handlerGen` and `middlewareGen` effects, so Effect runs their finalizers, such as `Effect.ensuring`, `Effect.onInterrupt`, and releases of `Effect.acquireRelease`. The call then rejects with the signal's reason:

```ts
const procedure = os.handler(handlerGen(function* () {
  return yield* Effect.scoped(Effect.gen(function* () {
    const connection = yield* Effect.acquireRelease(
      openConnection,
      connection => connection.close,
    )

    // On abort, the query is interrupted and the connection is closed
    return yield* connection.query('SELECT ...')
  }))
}))
```

:::info
Handlers don't get a `Scope`, so wrap code that acquires scoped resources in `Effect.scoped`. On Cloudflare Workers, enable the [`enable_request_signal`](/docs/adapters/cloudflare-workers#compatibility-flags) compatibility flag so the request signal is aborted.
:::

## Effectful Middleware

`middlewareGen` allows you to write effectful middleware using generator functions. Inside the generator, you can yield Effect operations and `yield* next()` to continue the chain. Downstream failures land in the error channel of `next`, so you can recover from them with Effect.

```ts twoslash
import { os } from '@orpc/server'
// ---cut---
import { middlewareGen } from '@orpc/experimental-effect'
import { Clock } from 'effect'

const procedure = os
  .$context<{ auth: boolean }>()
  .use(middlewareGen(function* ({ context, next }) {
    const startedAt = yield* Clock.currentTimeMillis
    return yield* next({ context: { startedAt } })
  }))
  .handler(({ context }) => context.startedAt)
```

## Client Calls

`createEffectClient` wraps any oRPC client, whether [server-side](/docs/client/server-side) or [client-side](/docs/client/client-side), so every procedure returns a lazy Effect instead of a promise, ready to `yield*` inside Effect generators. The output becomes the success value, and errors land in the error channel with their original types preserved, ready for utilities like `catchORPCErrorCodes`:

```ts
import { catchORPCErrorCodes, createEffectClient } from '@orpc/experimental-effect'
import { Effect } from 'effect'

const effectClient = createEffectClient(client)

const program = Effect.gen(function* () {
  const planet = yield* effectClient.planet.find({ id: 1 })
  return planet.name
}).pipe(
  catchORPCErrorCodes({
    NOT_FOUND: error => Effect.succeed('unknown'),
  }),
)
```

For typed `error.data`, combine `Effect.catchIf` with [isDefinedError](/docs/client/error-handling#using-safe-and-isdefinederror):

```ts
import { isDefinedError } from '@orpc/client'
import { Effect } from 'effect'

const recovered = effectClient.planet.find({ id: 1 }).pipe(
  Effect.catchIf(isDefinedError, (error) => {
    // error and error.data are fully typed here
    return Effect.succeed(null)
  }),
)
```

:::info
The effects are lazy: the client is invoked each time the effect runs, so they work naturally with `Effect.retry`. Interrupting the effect aborts the underlying call.
:::

## Effect Schema

oRPC natively supports [Standard Schema](https://standardschema.dev/schema#what-schema-libraries-implement-the-spec), and [Effect Schema](https://effect.website/docs/schema/introduction/) implements that spec through [Schema.toStandardSchemaV1](https://effect.website/docs/schema/standard-schema/):

```ts
import { Schema } from 'effect'

const procedure = os
  .input(Schema.toStandardSchemaV1(Schema.Struct({ name: Schema.String })))
  .handler(handlerGen(function* ({ input, context }) {
    return `Hello ${input.name}!`
  }))
```

### `.input` and `.output` Extensions

Import `@orpc/experimental-effect/extensions/input-output` from a module that always runs during initialization, such as the file where you define your base builder or create your server. This lets you define `.input` and `.output` directly with Effect Schema:

<CodeGroup>

```ts usage
const procedure = base
  .input(Schema.Struct({ name: Schema.String }))
  .output(Schema.Struct({ greeting: Schema.String }))
  .handler(handlerGen(function* ({ input, context }) {
    return { greeting: `Hello ${input.name}!` }
  }))
```

```ts setup
import '@orpc/experimental-effect/extensions/input-output'

import { os } from '@orpc/server'

export const base = os
```

</CodeGroup>

:::info
You can also use these extensions with the [contract builder](/docs/contract/procedure).
:::

### JSON Schema Converter

This integration also provides `EffectSchemaToJsonSchemaConverter`, which wraps Effect's built-in [Schema.toJsonSchemaDocument](https://effect.website/docs/schema/json-schema/). Use it with tools such as the [OpenAPI Generator](/docs/openapi/specification#openapi-generator). It accepts the same options as `Schema.toJsonSchemaDocument`, such as `onExcessProperty`, `generateDescriptions`, `includeAnnotationKey`, and `referencePolicy`:

```ts
import { EffectSchemaToJsonSchemaConverter } from '@orpc/experimental-effect'

const generator = new OpenAPIGenerator({
  converters: [
    new EffectSchemaToJsonSchemaConverter({
      onExcessProperty: 'error',
    }),
  ],
})
```

Schemas with an `identifier` annotation, including `Schema.Class` and recursive schemas, are preserved in `$defs`, which `OpenAPIGenerator` can then [hoist](/docs/openapi/specification#hoisting-defs) into `components.schemas`.

:::tip
Enable the `cache` option to reuse conversion results when the same schema instance is converted repeatedly. When enabled, repeated conversions return the same JSON schema object, so treat the results as immutable.

```ts
const converter = new EffectSchemaToJsonSchemaConverter({ cache: true })
```

:::

## OpenTelemetry Integration

First, set up the [oRPC OpenTelemetry integration](/docs/integrations/opentelemetry). Then install [`@effect/opentelemetry`](https://www.npmjs.com/package/@effect/opentelemetry) and add `OtelTracer.layerGlobal` to the layer of your [runtime](#providing-services-with-layers). Effect's tracer then uses the globally registered OpenTelemetry tracer provider, so spans from `Effect.withSpan` and `Effect.fn('name')` are exported with oRPC's spans and nested under them:

```package-install
npm install @effect/opentelemetry
```

```ts
import { OtelTracer } from '@effect/opentelemetry'
import { Layer, ManagedRuntime } from 'effect'

const runtime = ManagedRuntime.make(
  AppLayer.pipe(Layer.provideMerge(OtelTracer.layerGlobal)),
)

export async function fetch(request: Request) {
  const { matched, response } = await handler.handle(request, {
    context: {
      'effect/context': await runtime.context(),
    },
  })

  if (matched) {
    return response
  }

  return new Response('Not Found', { status: 404 })
}
```

:::info
`OtelTracer.layerGlobal` needs no `Resource` layer, because the resource and exporters belong to the tracer provider you registered, for example with `NodeSDK`. Without other services, use `ManagedRuntime.make(OtelTracer.layerGlobal)`.
:::

## Testing

Effectful procedures get their services from `effect/context`, so with [`@effect/vitest`](https://www.npmjs.com/package/@effect/vitest) you can provide test layers and pass the test's context to the procedure. See [Testing and Mocking](/docs/recipes/testing-and-mocking) for general testing patterns:

```ts
import { assert, layer } from '@effect/vitest'
import { call } from '@orpc/server'
import { Effect, Layer } from 'effect'

const RandomTest = Layer.succeed(Random, Random.of({ next: Effect.succeed(0.5) }))

layer(RandomTest)('random', (it) => {
  it.effect('returns the next random number', () =>
    Effect.gen(function* () {
      const context = yield* Effect.context<Random>()

      const result = yield* Effect.promise(() =>
        call(procedure, undefined, { context: { 'effect/context': context } }),
      )

      assert.strictEqual(result, 0.5)
    }))
})
```

The context also holds test services such as `TestClock`, so the procedure sees the same time as the test.

## Cloudflare Workers

On Cloudflare Workers, Effect recommends running the whole application on a sync scheduler, `new Scheduler.MixedScheduler('sync')`, because timers owned by one request can be discarded and leave shared fibers suspended. Provide it to your layers, and through `effect/context` to every request, and create the runtime at module scope:

```ts
import { Layer, ManagedRuntime, Scheduler } from 'effect'

const SyncScheduler = Layer.succeed(
  Scheduler.Scheduler,
  new Scheduler.MixedScheduler('sync'),
)

// Start building at module scope: fibers started inside `fetch` capture that request's async context
const runtime = ManagedRuntime.make(AppLayer.pipe(Layer.provideMerge(SyncScheduler)))
const effectContext = runtime.context()

export default {
  async fetch(request: Request) {
    const { matched, response } = await handler.handle(request, {
      context: {
        'effect/context': await effectContext,
      },
    })

    if (matched) {
      return response
    }

    return new Response('Not Found', { status: 404 })
  },
}
```

Layer construction can't use request-time I/O, so read bindings from the `env` export of `cloudflare:workers`. Without layers, add the scheduler to the context directly with `Context.add(Scheduler.Scheduler, new Scheduler.MixedScheduler('sync'))`.

:::warning
The sync scheduler doesn't yield to the event loop, so CPU-heavy effects delay other requests, and it doesn't fix request-owned timers such as `Effect.sleep`. See `Scheduler.MixedScheduler` in Effect for details.
:::

## Next.js

Next.js functions such as [redirect](https://nextjs.org/docs/app/api-reference/functions/redirect) and [notFound](https://nextjs.org/docs/app/api-reference/functions/not-found) throw special errors. Thrown inside an effect, they become defects, which oRPC rethrows unchanged, so [Server Functions](/docs/integrations/next#server-functions) still hand them to Next.js. A handler that catches defects, such as `Effect.catchCause`, `Effect.catchDefect`, or a catch-all in `effect/wrap`, swallows them unless it rethrows them first with [unstable_rethrow](https://nextjs.org/docs/app/api-reference/functions/unstable_rethrow):

```ts
import { Cause, Effect } from 'effect'
import { unstable_rethrow } from 'next/navigation'

const procedure = os.handler(handlerGen(function* () {
  return yield* loadDashboard.pipe( // may call redirect() or notFound()
    Effect.catchCause((cause) => {
      unstable_rethrow(Cause.squash(cause))
      return Effect.succeed(fallbackDashboard)
    }),
  )
}))
```
