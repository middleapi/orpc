:::

## Installation

```package-install
npm install @orpc/msw@beta
```

## Setup

Create MSW utils from a [router contract](/docs/contract/router) or an implemented [router](/docs/router). The `handler` option creates the fetch handler serving each mock, typically a [RPC Handler](/docs/rpc/handler) configured like your production one, so serialization, validation, and error envelopes always behave exactly like your production server.

```ts
import { createMSWUtils } from '@orpc/msw'
import { RPCHandler } from '@orpc/server/fetch'

export const mock = createMSWUtils(contract, {
  url: 'https://example.com/rpc',
  handler: router => new RPCHandler(router),
})
```

The `url` option must match the URL your [RPC Link](/docs/rpc/link) sends requests to and supports MSW wildcards, such as `*/rpc` to match any origin.

:::info
When you mock an implemented router, only the mock implementations run. The real handlers and middleware are never invoked.
:::

## Mocking Procedures

The `.handler` method creates an MSW request handler that resolves a procedure. The input is deserialized and validated before your mock runs, and the return value is validated against the output schema and serialized with the [RPC serializer](/docs/rpc/serializer), so types like `Date`, `Map`, or `BigInt` reach the client intact.

```ts
import { setupServer } from 'msw/node'

const server = setupServer(
  mock.planet.list.handler(({ input }) => [
    { id: 1, name: 'Earth' },
  ]),
)

server.listen()
```

Beyond `input`, the mock also receives the MSW resolver information, such as the raw `request`.

:::info
[AsyncIteratorObject](/docs/async-iterator-object) outputs work too: return an async generator and the client receives a streamed response.
:::

## Mocking Errors

The `.error` method creates an MSW request handler that rejects a procedure with an error defined in the contract, serialized exactly like a server-thrown error. Inside `.handler`, you can also throw typed errors dynamically via the `errors` constructors.

```ts
const handlers = [
  mock.planet.find.error('NOT_FOUND', { data: { id: 123 } }),
  mock.planet.update.handler(({ input, errors }) => {
    throw errors.CONFLICT({ data: { id: input.id } })
  }),
]
```

## Mocking Loading States

The `.loading` method creates an MSW request handler that never resolves, useful for testing loading states, for example in [Storybook](https://storybook.js.org/docs/writing-stories/mocking-data-and-modules/mocking-network-requests) stories:

```ts
export const Loading: Story = {
  parameters: {
    msw: {
      handlers: [mock.planet.list.loading()],
    },
  },
}
```

## Passthrough

The `.passthrough` method creates an MSW request handler that performs matching requests against the real server as-is, useful to exempt specific procedures from mocking, for example while [onUnhandledRequest](https://mswjs.io/docs/api/setup-server/listen#onunhandledrequest) treats everything else as an error:

```ts
const handlers = [
  mock.planet.list.handler(() => []),
  mock.planet.find.passthrough(), // hits the real server
]
```

## OpenAPI Protocol

By default, procedure URLs are matched following the [RPC protocol](/docs/rpc/handler). If your client uses the [OpenAPI Link](/docs/openapi/link), pass `protocol: 'openapi'` and create an [OpenAPI Handler](/docs/openapi/handler) instead. Requests are then matched against each procedure's [route](/docs/openapi/routing), including custom methods, prefixes, and path parameters such as `/planets/{id}` or greedy `/files/{+path}` segments.

```ts
import { OpenAPIHandler } from '@orpc/openapi/fetch'

const mock = createMSWUtils(contract, {
  protocol: 'openapi',
  url: '*/api',
  handler: router => new OpenAPIHandler(router),
})
```

Everything else works the same: `.handler` receives the deserialized input, `.error` responds with typed errors, and the OpenAPI serializer handles the response, so the mocked client behaves exactly like one talking to a real OpenAPI Handler.

## Advanced Configuration

All handler behavior is configured through the `handler` option, so mocks can mirror your production setup exactly, such as plugins, a custom serializer, or `allowMethods` if your client sends [GET requests](/docs/rpc/handler#supported-http-methods) over the RPC protocol:

```ts
import { RPCHandler } from '@orpc/server/fetch'
import { ResponseHeadersPlugin } from '@orpc/server/plugins'

const mock = createMSWUtils(contract, {
  url: '*/rpc',
  handler: router => new RPCHandler(router, {
    plugins: [new ResponseHeadersPlugin()],
  }),
})
```

You can also disable validation of the mocked data:

```ts
const mock = createMSWUtils(contract, {
  url: '*/rpc',
  handler: router => new RPCHandler(router),
  disableOutputValidation: true,
})
```

Each mock serves a router containing only the procedure being mocked, and URL matching follows the `protocol` option, so make sure the handler you create speaks the same protocol. Requests the created handler does not match simply fall through to other MSW handlers.

## Limitations

Requests sent through the [Batch Requests Plugin](/docs/plugins/batch) cannot be mocked. Each mock serves a router containing only its own procedure, so even a `handler` configured with the batch plugin cannot resolve the other procedures bundled into the same HTTP request. Disable batching when mocking with MSW.
