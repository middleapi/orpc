## Installation

```package-install
npm install @orpc/ratelimit@beta
```

## Basic Usage

The core concept is the `RateLimiter` interface, which defines a standard way to check and enforce rate limits. You can create your own custom limiter or use one of the provided [adapters](#adapters):

| Name                                   | Blocking Mode | Adapter for                                                                                               |
| -------------------------------------- | ------------- | --------------------------------------------------------------------------------------------------------- |
| [`MemoryRateLimiter`](#memory)         | ✅            | In-memory storage                                                                                         |
| [`RedisRateLimiter`](#redis)           | ✅            | [Redis](https://github.com/redis/redis)                                                                   |
| [`UpstashRateLimiter`](#upstash)       | ✅            | [Upstash Redis](https://github.com/upstash/redis-js)                                                      |
| [`BunRedisRateLimiter`](#bun-redis)    | ✅            | [Bun's Redis](https://bun.com/docs/runtime/redis)                                                         |
| [`CloudflareRateLimiter`](#cloudflare) | ❌            | [Cloudflare's Rate Limiting](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/) |

The `limit` method accepts a key and an optional `weight` value, which defaults to `1`, so a single request can consume multiple points.

```ts twoslash
import { MemoryRateLimiter } from '@orpc/ratelimit/memory'
// ---cut---
import { ORPCError } from '@orpc/server'

const limiter = new MemoryRateLimiter({
  maxRequests: 5,
  window: 60000,
})

const result = await limiter.limit('user:123', { weight: 2 })

if (!result.success) {
  throw new ORPCError('TOO_MANY_REQUESTS', {
    data: {
      limit: result.limit,
      remaining: result.remaining,
      reset: result.reset,
    },
  })
}
```

### Algorithm

The memory and Redis-based adapters share the same fixed-window algorithm, so switching between them does not change behavior:

- **Per-key windows**: each key has its own window of `window` milliseconds, starting at the first request that consumes quota for that key. When it ends, the next request starts a new one.
- **Rejected requests are free**: a request passes only when its `weight` still fits in the key's window. One that does not fit is rejected without consuming anything, so a client that keeps retrying does not push its own reset further away, and a smaller request can still use what is left.
- **Result**: `limit` is `maxRequests`, `remaining` is the quota left in the key's window, and `reset` is the Unix timestamp in milliseconds at which that window ends.

[`CloudflareRateLimiter`](#cloudflare) is the exception: the Workers Rate Limiting binding runs its own algorithm and only reports `success`.

### Blocking Mode

Some adapters support blocking mode, which waits until capacity becomes available instead of rejecting requests immediately. Set `timeout` to how long a request may wait, in milliseconds. A request still fails right away when its window will not reset before the timeout elapses. Waiting consumes no quota.

```ts
const limiter = new MemoryRateLimiter({
  maxRequests: 10,
  window: 60000,
  timeout: 5000, // Wait up to 5 seconds, 0 (no waiting) by default
})
```

## Ratelimit Middleware

The `ratelimit` helper creates middleware that enforces rate limits for [procedures](/docs/procedure).

```ts
import { ratelimit, RateLimiter } from '@orpc/ratelimit'

const procedure = os
  .$context<{ ratelimiter: RateLimiter }>()
  .input(z.object({ email: z.email() }))
  .use(
    ratelimit({
      limiter: ({ context }) => context.ratelimiter,
      key: ({ context }, input) => `login:${input.email}`,
      weight: 1, // Optional weight for each request, default is 1
    }),
  )
  .handler(({ input }) => {
    return { success: true }
  })

const ratelimiter = new MemoryRateLimiter({
  maxRequests: 10,
  window: 60000,
})

const result = await call(procedure, { email: 'user@example.com' }, { context: { ratelimiter } })
```

:::info[Automatic Deduplication]
When the same `limiter` and `key` combination is used multiple times in a single request chain, the `ratelimit` middleware performs the rate limit check only once. This behavior follows the [Dedupe Middleware](/docs/recipes/dedupe-middleware) recipe. To disable deduplication, set `dedupe: false`.
:::

:::tip[Custom Error]
By default the middleware throws `TOO_MANY_REQUESTS`. Use `error` to throw your own, which is [defined](/docs/error-handling#orpcerror-compatibility) when its `code` and `data` match an error the procedure declares. A custom code responds with `400` unless you map it in [`errorStatusMap`](/docs/rpc/handler#custom-error-response).

```ts
ratelimit({
  limiter,
  key,
  error: (result) => new ORPCError('RATE_LIMITED', { data: { reset: result.reset } }),
})
```

:::

:::tip[Conditional Limiter]
You can choose different limiters dynamically based on the request context:

```ts
const premiumLimiter = new MemoryRateLimiter({
  maxRequests: 100,
  window: 60000,
})

const standardLimiter = new MemoryRateLimiter({
  maxRequests: 10,
  window: 60000,
})

const result = await call(
  procedure,
  { email: 'user@example.com' },
  {
    context: {
      ratelimiter: isPremiumUser ? premiumLimiter : standardLimiter,
    },
  },
)
```

:::

## Handler Plugin

The `RateLimitHandlerPlugin` automatically adds HTTP rate limiting headers (`RateLimit-*` and `Retry-After`) to responses when used with [Ratelimit Middleware](#ratelimit-middleware). This lets clients inspect the current limit state and know when they can retry after hitting a limit.

```ts
import { RateLimitHandlerPlugin } from '@orpc/ratelimit'

const handler = new RPCHandler(router, {
  plugins: [new RateLimitHandlerPlugin()],
})
```

| Header                | Value                                                                  |
| --------------------- | ---------------------------------------------------------------------- |
| `RateLimit-Limit`     | Maximum number of requests allowed within a window                     |
| `RateLimit-Remaining` | Requests left in the current window                                    |
| `RateLimit-Reset`     | Seconds until the window resets, rounded up                            |
| `Retry-After`         | Same value as `RateLimit-Reset`, only on a rejected request's response |

`RateLimit-Reset` is a number of seconds from now, as in the [IETF RateLimit header drafts](https://datatracker.ietf.org/doc/draft-ietf-httpapi-ratelimit-headers/), not the timestamp found in `result.reset`. A header is omitted when the limiter does not report its value.

:::info
You can combine this plugin with [Retry After Plugin](/docs/plugins/retry-after) to enable automatic client-side retries based on server rate limiting headers.
:::

:::info
The `handler` can be any supported oRPC handler, such as [RPCHandler](/docs/rpc/handler), [OpenAPIHandler](/docs/openapi/handler), or a custom one.
:::

## Adapters

### Memory

Keeps counters in the memory of the current process, so limits are not shared between instances. A good fit for development, tests, and single-process servers.

```ts
import { MemoryRateLimiter } from '@orpc/ratelimit/memory'

const limiter = new MemoryRateLimiter({
  /**
   * Maximum number of requests allowed within the window.
   */
  maxRequests: 10,

  /**
   * The duration of the fixed window in milliseconds.
   */
  window: 60000,

  /**
   * How long to wait for capacity to become available, in milliseconds.
   * Gives up right away when the window will not reset before the timeout elapses.
   *
   * @default 0
   */
  timeout: 0,
})
```

### Redis

Stores counters in Redis, so every instance using the same server enforces the same limits. Keys are stored as `prefix + key`, and limiters with the same prefix share counters.

```ts
import { RedisRateLimiter } from '@orpc/ratelimit/redis'
import { createClient } from 'redis'

const client = createClient({ url: 'redis://localhost:6379' })

// RedisRateLimiter lazily connects to Redis when needed.
// You can still call `client.connect()` manually, but it is optional.
await client.connect()

const limiter = new RedisRateLimiter(client, {
  /**
   * The prefix to use for Redis keys.
   *
   * @default 'orpc:ratelimit:'
   */
  prefix: 'orpc:ratelimit:',

  /**
   * Maximum number of requests allowed within the window.
   */
  maxRequests: 10,

  /**
   * The duration of the fixed window in milliseconds.
   */
  window: 60000,

  /**
   * How long to wait for capacity to become available, in milliseconds.
   * Gives up right away when the window will not reset before the timeout elapses.
   *
   * @default 0
   */
  timeout: 0,
})

// Creates a limiter with an extra prefix that shares this client, e.g. per tenant
const tenantLimiter = limiter.prefix('tenant:123:')
```

const redis = Redis.fromEnv()

const limiter = new UpstashRateLimiter(redis, {

### Cloudflare

Uses the Workers Rate Limiting binding, so limits are configured in your Worker settings rather than in the adapter. The binding decides how requests are counted, so the [algorithm](#algorithm) above does not apply: it reports only `success`, and a request with a `weight` above `1` that gets rejected partway has already consumed part of it.

```ts
import { CloudflareRateLimiter } from '@orpc/cloudflare'

export default {
  async fetch(request, env) {
    const limiter = new CloudflareRateLimiter(env.MY_RATE_LIMITER, {
      /**
       * The prefix to use for cloudflare ratelimit.
       *
       * @default ''
       */
      prefix: '',
    })

    // Creates a limiter with an extra prefix that shares this binding, e.g. per tenant
    const tenantLimiter = limiter.prefix('tenant:123:')
  },
}
```
