oRPC, [tRPC](https://trpc.io/), and [Hono](https://hono.dev/) all give you end-to-end typesafe APIs in TypeScript without code generation. tRPC is RPC for TypeScript clients, Hono is a web framework with a typed client, and oRPC is RPC that also serves the same procedures as a RESTful API with an OpenAPI spec.

tRPC and Hono claims were last checked on October 24, 2026, against tRPC 11.19.0 and Hono 4.13.13. See [Sources](#sources).

## At a Glance

|  | oRPC | tRPC | Hono |
| --- | --- | --- | --- |
| API style | RPC and RESTful routes from one router | RPC | RESTful routes |
| OpenAPI | First-party | Official `@trpc/openapi` (alpha), RPC-shaped paths only | Third-party middleware |
| Contract-first | First-party | Not supported | Third-party middleware |
| Data types | JSON plus `Date`, `Map`, `Set`, `BigInt`, `File`, streams, ... | JSON, more with a transformer | JSON |

## When to Choose oRPC

- You need a [RESTful API](/docs/openapi/handler) or an [OpenAPI spec](/docs/openapi/specification) from the same procedures your client calls.
- You want to [design a contract first](/docs/contract-first) and share only the contract with clients.
- Your procedures return [files or binary streams](/docs/binary-data) and you want them typed.
- You use `Date`, `Map`, `BigInt`, or `File` without configuring a [transformer](/docs/rpc/serializer#supported-data-types).
- You use [TanStack Query](/docs/integrations/tanstack-query) outside React, or want first-party [MCP](/docs/integrations/mcp), [AI SDK](/docs/integrations/ai-sdk), [NestJS](/docs/integrations/nest), or [OpenTelemetry](/docs/integrations/opentelemetry) integrations.

## When tRPC May Fit Better

- You want a stable major version: tRPC v11 is stable, while oRPC v2 is in beta.
- Your team or starter (such as [create-t3-app](https://create.t3.gg/)) already uses tRPC. tRPC is older, with a much larger community.
- Your tRPC app works and needs none of the features above.

## When Hono May Fit Better

- You are building a web server first (routing, middleware, HTML, static files) and a typed client is a bonus.
- You design the HTTP interface by hand, and your app is small enough that Hono's [RPC types stay fast](https://hono.dev/docs/guides/rpc#known-issues).

## Use Them Together

- **tRPC:** [`toORPCRouter`](/docs/integrations/trpc) converts a tRPC router into an oRPC router, so you can serve it with the [OpenAPI Handler](/docs/openapi/handler) and [migrate](/docs/migrations/from-trpc) later, if at all.
- **Hono:** the [Hono adapter](/docs/adapters/hono) mounts oRPC as Hono middleware.

```ts
import { OpenAPIHandler } from '@orpc/openapi/fetch'
import { toORPCRouter } from '@orpc/trpc'

const handler = new OpenAPIHandler(toORPCRouter(trpcRouter))
```

## The Same Endpoint in Each

The `openapi` line is optional: it gives the oRPC procedure the RESTful route `GET /planets/{id}`.

<CodeGroup>

```ts oRPC
import { openapi } from '@orpc/openapi'
import { ORPCError, os } from '@orpc/server'
import * as z from 'zod'

const planets = [{ id: 'earth', name: 'Earth' }]

export const router = {
  planet: {
    find: os
      .meta(openapi({ method: 'GET', path: '/planets/{id}' }))
      .input(z.object({ id: z.string() }))
      .handler(async ({ input }) => {
        const planet = planets.find(planet => planet.id === input.id)
        if (!planet) {
          throw new ORPCError('NOT_FOUND')
        }
        return planet
      }),
  },
}
```

```ts tRPC
import { initTRPC, TRPCError } from '@trpc/server'
import * as z from 'zod'

const planets = [{ id: 'earth', name: 'Earth' }]

const t = initTRPC.create()

export const appRouter = t.router({
  planet: t.router({
    find: t.procedure
      .input(z.object({ id: z.string() }))
      .query(async ({ input }) => {
        const planet = planets.find(planet => planet.id === input.id)
        if (!planet) {
          throw new TRPCError({ code: 'NOT_FOUND' })
        }
        return planet
      }),
  }),
})

export type AppRouter = typeof appRouter
```

```ts Hono
import { zValidator } from '@hono/zod-validator'
import { Hono } from 'hono'
import * as z from 'zod'

const planets = [{ id: 'earth', name: 'Earth' }]

const app = new Hono().get(
  '/planets/:id',
  zValidator('param', z.object({ id: z.string() })),
  async (c) => {
    const { id } = c.req.valid('param')
    const planet = planets.find(planet => planet.id === id)
    if (!planet) {
      return c.json({ error: 'Planet not found' }, 404)
    }
    return c.json(planet, 200)
  },
)

export type AppType = typeof app
```

</CodeGroup>

On the client, oRPC calls `client.planet.find({ id })`, tRPC calls `trpc.planet.find.query({ id })`, and Hono calls `client.planets[':id'].$get({ param: { id } })`, which returns a typed `Response`.

## Features

- ✅ First-class, built-in support
- 🟡 Lacks features or requires third-party integrations
- 🛑 Not supported or not documented

Ratings for tRPC and Hono are sourced under [Sources](#sources).

### Type Safety

| Feature | oRPC | tRPC | Hono |
| --- | --- | --- | --- |
| End-to-end typesafe input/output | ✅ | ✅ | ✅ |
| [End-to-end typesafe errors](/docs/client/error-handling) | ✅ | 🟡 | ✅ |
| [End-to-end typesafe File/Blob](/docs/binary-data) | ✅ | 🟡 | 🟡 |
| [End-to-end typesafe Server-Sent Events](/docs/async-iterator-object) | ✅ | ✅ | 🛑 |
| [End-to-end typesafe `ReadableStream<Uint8Array>`](/docs/binary-data#readablestreamuint8array) | ✅ | 🛑 | 🛑 |
| [Typesafe at scale](#type-checking-performance) | ✅ | ✅ | 🛑 |

oRPC types errors per procedure or globally, with [declared errors](/docs/error-handling) or an [error factory](/docs/error-handling#error-factory). tRPC (as of 11.19) has one global `errorFormatter`. Hono types errors returned with a status code, such as `c.json({ error }, 404)`, but not a thrown `HTTPException`. Only oRPC types binary responses; tRPC and Hono type uploads only.

### API Design & OpenAPI

| Feature | oRPC | tRPC | Hono |
| --- | --- | --- | --- |
| Implementation-first approach | ✅ | ✅ | ✅ |
| [Contract-first approach](/docs/contract-first) | ✅ | 🛑 | 🟡 |
| [OpenAPI spec generation](/docs/openapi/specification) | ✅ | 🟡 | 🟡 |
| [Standard Schema (Zod, Valibot, ArkType, ...)](/docs/integrations/standard-schema) | ✅ | ✅ | 🟡 |
| [Native types (Date, URL, Set, Map, ...)](/docs/rpc/serializer#supported-data-types) | ✅ | 🟡 | 🛑 |
| [Custom serializers](/docs/rpc/serializer#custom-serializers) | ✅ | ✅ | 🛑 |
| [Bracket notation (nested query and form data)](/docs/openapi/bracket-notation) | ✅ | 🛑 | 🟡 |
| [Lazy router (code splitting, faster cold starts)](/docs/router#lazy-router) | ✅ | ✅ | 🛑 |

oRPC serves one router over its [RPC protocol](/docs/rpc/protocol) and as [RESTful routes](/docs/openapi/handler). tRPC's `@trpc/openapi` is in alpha and only describes its RPC endpoints, and Hono's OpenAPI and contract-first support come from third-party middleware such as `@hono/zod-openapi`. tRPC needs a transformer for types like `Date`, and Hono sends JSON only. Hono parses nested form fields with `parseBody({ dot: true })`.

## Performance

:::warning
Treat these numbers as reference measurements, not a reason to switch frameworks. All three are fast enough for production. The per-request difference is tiny next to your business logic, database, and network, and results vary across environments and workloads.
:::

All numbers come from [middleapi/orpc-benchmarks](https://github.com/middleapi/orpc-benchmarks) and were measured on the same machine with oRPC 2.0.0-beta.37, tRPC 11.19.0, and Hono 4.13.8. Handlers are no-ops with pass-through validation, so the results measure framework overhead only.

### Throughput

| Scenario | oRPC | tRPC | Hono |
| --- | --- | --- | --- |
| RPC over HTTP (req/s avg) | 20,279 | 4,821 | n/a |
| RPC over WebSocket (req/s avg) | 22,979 | 5,228 | n/a |
| OpenAPI (RESTful) over HTTP (req/s avg) | 19,799 | n/a | 18,694 |

oRPC handles about 4.2x as many requests as tRPC over HTTP and 4.4x over WebSocket. oRPC and Hono are close on RESTful throughput, with oRPC about 6% ahead.

### Clinic Doctor Profiles

Every run also profiles the server with [Clinic.js Doctor](https://clinicjs.org/doctor/):

| Run | CPU (avg) | Memory (RSS) | Detected issues | Full report |
| --- | --- | --- | --- | --- |
| RPC over HTTP · oRPC | ~104% | 71-87 MB | none | [view](https://htmlpreview.github.io/?https://github.com/middleapi/orpc-benchmarks/blob/main/benchmarks/rpc-orpc/.clinic/report.clinic-doctor.html) |
| RPC over HTTP · tRPC | ~113% | 75-248 MB | none | [view](https://htmlpreview.github.io/?https://github.com/middleapi/orpc-benchmarks/blob/main/benchmarks/rpc-trpc/.clinic/report.clinic-doctor.html) |
| RPC over WebSocket · oRPC | ~104% | 72-107 MB | none | [view](https://htmlpreview.github.io/?https://github.com/middleapi/orpc-benchmarks/blob/main/benchmarks/ws-orpc/.clinic/report.clinic-doctor.html) |
| RPC over WebSocket · tRPC | ~40% | 68-77 MB | cpu: performance | [view](https://htmlpreview.github.io/?https://github.com/middleapi/orpc-benchmarks/blob/main/benchmarks/ws-trpc/.clinic/report.clinic-doctor.html) |
| OpenAPI over HTTP · oRPC | ~104% | 72-90 MB | none | [view](https://htmlpreview.github.io/?https://github.com/middleapi/orpc-benchmarks/blob/main/benchmarks/openapi-orpc/.clinic/report.clinic-doctor.html) |
| OpenAPI over HTTP · Hono | ~103% | 77-95 MB | none | [view](https://htmlpreview.github.io/?https://github.com/middleapi/orpc-benchmarks/blob/main/benchmarks/openapi-hono/.clinic/report.clinic-doctor.html) |

The profiles show where the throughput gap comes from. Over HTTP, oRPC serves over 4x tRPC's requests at similar CPU usage (~104% vs ~113%), so its per-request CPU cost is several times lower, and its event loop stays responsive: 0.04 ms average delay versus tRPC's 0.77 ms. Memory stays flat between 71 and 107 MB in every oRPC run, while tRPC's HTTP run climbs to 248 MB, more than double oRPC's highest reading, a sign of per-request allocation pressure. oRPC and Hono profile nearly identically, in line with their close throughput.

tRPC's low WebSocket CPU is not an advantage: the `cpu: performance` issue means the server cannot keep the CPU busy, so throughput is capped elsewhere in the stack.

### Type-Checking Performance

On a large, fully typed project with 3,000 procedures across 1,501 routers, oRPC type-checks about 30% faster than tRPC, uses about 31% less memory, and needs about 19% fewer type instantiations:

| Metric | oRPC | tRPC |
| --- | --- | --- |
| Total time | 1.62s | 2.32s |
| Memory used | 469 MB | 677 MB |
| Instantiations | 2,198,304 | 2,719,560 |

Hono has no column because it does not scale to this size. Its RPC types hit [known limits](https://hono.dev/docs/guides/rpc#known-issues) well before this point and the project becomes effectively unusable, an issue oRPC avoids by design.

## FAQ

### Is oRPC a tRPC alternative?

Yes. Like tRPC, you define procedures in a router and call them from a fully typed client, and most concepts map one to one (see the [migration guide](/docs/migrations/from-trpc#core-concepts-comparison)). oRPC adds RESTful routes, an OpenAPI spec, contract-first, and native types without a transformer.

### Can I use oRPC with an existing tRPC router?

Yes. `toORPCRouter` from `@orpc/trpc` turns it into an oRPC router you can serve with oRPC's RPC or OpenAPI handlers. tRPC error formatting is not carried over. See [tRPC Integration](/docs/integrations/trpc).

### Does tRPC support OpenAPI?

Partly. The official `@trpc/openapi` (alpha) generates a spec for tRPC's own endpoints (`GET` or `POST /procedure.path`), without subscriptions or RESTful routes. To serve a tRPC router as OpenAPI, [wrap it with oRPC](#use-them-together).

### Can I use oRPC with Hono?

Yes. The [Hono adapter](/docs/adapters/hono) mounts oRPC as Hono middleware, and hono.dev lists oRPC among its [third-party middleware](https://hono.dev/docs/middleware/third-party).
