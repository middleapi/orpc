---

[OpenRPC Handler](/docs/openrpc/handler) serves your procedures over [JSON-RPC 2.0](https://www.jsonrpc.org/specification), [OpenRPC Link](/docs/openrpc/link) calls them, and the [OpenRPC Generator](/docs/openrpc/specification) describes them in an [OpenRPC](https://open-rpc.org) document. The wire format is standard JSON-RPC 2.0 over HTTP `POST`, so any JSON-RPC client can call your procedures, such as [`@open-rpc/client-js`](https://github.com/open-rpc/client-js), clients in other languages, or `curl`.

:::info
oRPC supports the request/response part of JSON-RPC: single calls, batch requests, and client-to-server notifications. Streaming, files, and server-to-client notifications are not supported. See [Limitations](#limitations).
:::

## Methods

The JSON-RPC `method` is the procedure path joined with `.`:

```ts
const router = {
  planet: {
    find: os.handler(() => {}), // method "planet.find"
  },
  eth_getBalance: os.handler(() => {}), // method "eth_getBalance"
}
```

- Method names are case-sensitive.
- Names starting with `rpc.` are reserved by JSON-RPC. The handler never routes them to a procedure: `rpc.discover` is answered by the [Service Discovery](/docs/openrpc/specification#service-discovery) plugin, and any other `rpc.*` method is "Method not found".
- Router keys that are empty or contain `.` cannot be reached, because the method `a.b` always means the key `a`, then the key `b`. The [OpenRPC Generator](/docs/openrpc/specification#unsupported-procedures) reports them.
- Unknown methods, and procedures excluded by [`filter`](/docs/openrpc/handler#filtering-procedures) or because they [stream](#limitations), answer "Method not found" (`-32601`).

## Params

JSON-RPC sends `params` by-position (an array) or by-name (an object), while a procedure takes a single input. The handler maps them like this:

| `params`                         | Procedure input                                   |
| -------------------------------- | ------------------------------------------------- |
| Object (by-name)                 | The object                                        |
| `[input]` (by-position)          | `input`                                           |
| Absent, `null`, or `[]`          | [No input](#empty-params)                         |
| `{}`                             | [An empty object](#empty-params)                  |
| Array with more than one element | Error `-32602` "Invalid params"                   |
| Anything else                    | Error `-32600` "Invalid Request"                  |

An object input can be sent either way, as `{"id": 1}` or `[{"id": 1}]`. Any other input, such as a string, a number, an array, or a tuple, is sent by-position: `["Mars"]`, or `[[42, 23]]` for a tuple.

```bash
curl -X POST https://example.com/rpc \
  -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","method":"planet.rename","params":["Mars"],"id":2}'
```

:::info
`params: null` is not valid JSON-RPC, but the handler accepts it as absent params.
:::

### Empty Params

Generic clients send any of an absent `params`, `null`, `[]`, or `{}` for methods without required input. For example, [`@open-rpc/client-js`](https://github.com/open-rpc/client-js) always sends `params: []` when a call has no params. The handler resolves them to whichever empty input passes the input schema:

- Absent, `null`, and `[]` become `undefined`, unless only `{}` passes, as for `z.object({ limit: z.number().optional() })`.
- `{}` stays `{}`, unless only `undefined` passes, as for `z.void()`.

Params are plain JSON and are validated by the input schema as-is. Types such as `Date` or `BigInt` arrive as strings, so add the [Smart Coercion Plugin](/docs/plugins/smart-coercion) to the handler to coerce them before validation.

## Results

The `result` is the procedure output, serialized like an [OpenAPI response](/docs/openapi/serializer#supported-data-types):

| Output                                                                    | `result`                                |
| ------------------------------------------------------------------------- | --------------------------------------- |
| `undefined`                                                               | `null`, since `result` is required      |
| `Date`                                                                    | ISO string                              |
| `BigInt`, `URL`                                                           | String                                  |
| `Set`, `Map`                                                              | Array                                   |
| `NaN`, `Infinity`                                                         | `null`                                  |
| Properties set to `undefined`                                             | Omitted                                 |
| `Blob`, `File`, `ReadableStream`, `AsyncIteratorObject`, `FormData`       | Not sendable, error `-32603`            |

```bash
curl -X POST https://example.com/rpc \
  -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","method":"planet.find","params":{"id":1},"id":1}'
```

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"jsonrpc":"2.0","id":1,"result":{"id":1,"name":"Earth"}}
```

## Errors

When a procedure throws an [ORPCError](/docs/error-handling#orpcerror-class), the response carries a JSON-RPC error object:

```json
{
  "jsonrpc": "2.0",
  "id": 6,
  "error": {
    "code": -32004,
    "message": "Planet not found",
    "data": {
      "code": "NOT_FOUND",
      "defined": true,
      "data": { "id": 2 }
    }
  }
}
```

- `code` is the integer the oRPC error code maps to, see [Error Codes](#error-codes).
- `message` is the `ORPCError` message.
- `data` keeps the oRPC error code, whether the error is a [typesafe error](/docs/error-handling#typesafe-errors), and the error data (omitted when `undefined`), serialized like results. [OpenRPC Link](/docs/openrpc/link#error-responses) uses it to restore the exact `ORPCError`.

Input validation errors use `-32602` "Invalid params", with the issues in `data.data.issues`. Errors that are not an `ORPCError` become an `INTERNAL_SERVER_ERROR` with the message "Internal Server Error", so their details never leak.

Errors of the JSON-RPC layer itself are answered exactly as the specification shows, with its message and no `data`:

| Code     | Message          | Cause                                                                                             |
| -------- | ---------------- | ------------------------------------------------------------------------------------------------- |
| `-32700` | Parse error      | The body is empty, is not valid JSON, or cannot be decoded                                         |
| `-32600` | Invalid Request  | Not a request object: `jsonrpc` is not `"2.0"`, `method` is not a string, `params` is not structured, or `id` is invalid; or an empty batch |
| `-32601` | Method not found | No procedure serves the method                                                                    |
| `-32603` | Internal error   | A call failed outside procedure error handling, such as an interceptor throwing in a batch        |

The response `id` is the request `id`. For an invalid request object, it is the request `id` when one of a valid type was found, otherwise `null`, and a parse error always has `id: null`.

## Error Codes

oRPC error codes map to JSON-RPC error codes with `COMMON_JSON_RPC_ERROR_CODE_MAP`: `BAD_REQUEST` becomes "Invalid params", server errors become "Internal error", and other client errors become `-32000 - (status - 400)`, which keeps `-32700`, `-32600`, and `-32601` for the protocol errors above. Codes missing from the map fall back to `DEFAULT_JSON_RPC_ERROR_CODE` (`-32000`).

| PRECONDITION_FAILED    |        -32012 |              412 |

</Expandable>

Use `errorCodeMap` to map your own error codes. A given map replaces the default, so spread `COMMON_JSON_RPC_ERROR_CODE_MAP` to extend it, and pass the same map to the [OpenRPC Generator](/docs/openrpc/specification#errors) so the document lists the codes the handler sends:

```ts
import { COMMON_JSON_RPC_ERROR_CODE_MAP, OpenRPCGenerator } from '@orpc/openrpc'
import { OpenRPCHandler } from '@orpc/openrpc/fetch'

const errorCodeMap = {
  ...COMMON_JSON_RPC_ERROR_CODE_MAP,
  OUT_OF_STOCK: 1001,
}

const handler = new OpenRPCHandler(router, { errorCodeMap })

const spec = await new OpenRPCGenerator().generate(router, { errorCodeMap })
```

:::info
- JSON-RPC error codes must be integers, so a non-integer value throws a `TypeError` when the handler is created.
- JSON-RPC reserves `-32768` to `-32000` for the protocol and server errors, so pick codes outside this range for application errors.
- [OpenRPC Link](/docs/openrpc/link) needs no map, since the oRPC error code travels in `error.data.code`.
- The protocol error codes are exported as `JSON_RPC_ERROR_CODES`, such as `JSON_RPC_ERROR_CODES.METHOD_NOT_FOUND`.
:::

## Batch Requests

Send an array of request objects to make several calls in one HTTP request:

```bash
curl -X POST https://example.com/rpc \
  -H 'Content-Type: application/json' \
  -d '[
    {"jsonrpc":"2.0","method":"planet.find","params":{"id":1},"id":1},
    {"jsonrpc":"2.0","method":"planet.touch"},
    {"foo":"boo"},
    {"jsonrpc":"2.0","method":"planet.missing","id":"2"}
  ]'
```

```http
HTTP/1.1 200 OK
Content-Type: application/json

[
  {"jsonrpc":"2.0","id":1,"result":{"id":1,"name":"Earth"}},
  {"jsonrpc":"2.0","id":null,"error":{"code":-32600,"message":"Invalid Request"}},
  {"jsonrpc":"2.0","id":"2","error":{"code":-32601,"message":"Method not found"}}
]
```

- Calls run concurrently, and their responses keep the request order.
- Notifications get no response, and an invalid item gets an "Invalid Request" error in its place.
- A batch of one request still gets an array.
- A batch of only notifications gets an empty `204` response, never `[]`.
- An empty array `[]` gets a single "Invalid Request" error, not an array.
- Batches are limited to 100 requests by default, see [Batch Requests](/docs/openrpc/handler#batch-requests).

## Notifications

A request without an `id` member is a notification. The handler runs it to completion, then answers with an empty `204` response, or no entry in a batch response. Notification errors are never reported to the client.

```bash
curl -X POST https://example.com/rpc \
  -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","method":"planet.touch"}'
```

```http
HTTP/1.1 204 No Content
```

:::info
`"id": null` is a regular request, answered with `"id": null`, not a notification. Prefer string or number ids.
:::

## HTTP Transport

JSON-RPC requests are `POST` requests to the handler endpoint, such as `/rpc`, with one of these `Content-Type` headers (parameters such as `charset` are ignored):

- `application/json`
- `application/json-rpc`
- `application/jsonrequest`

Responses use `Content-Type: application/json` and these status codes:

| Response                                             | Status |
| ---------------------------------------------------- | -----: |
| Any JSON-RPC response or batch response              |  `200` |
| Single notification, or batch of only notifications  |  `204` |
| Unsupported `Content-Type`                           |  `415` |
| Body or batch too large                              |  `413` |

A single call can also use the status of its error, see [HTTP Status Codes](/docs/openrpc/handler#http-status-codes). A rejected HTTP request gets a JSON-RPC error with `id: null`:

```bash
curl -X POST https://example.com/rpc \
  -H 'Content-Type: text/plain' \
  -d '{"jsonrpc":"2.0","method":"planet.list","id":1}'
```

```http
HTTP/1.1 415 Unsupported Media Type
Content-Type: application/json

{"jsonrpc":"2.0","id":null,"error":{"code":-32015,"message":"JSON-RPC requests must use Content-Type: application/json","data":{"code":"UNSUPPORTED_MEDIA_TYPE","defined":false}}}
```

## Limitations

- **No streaming.** Procedures with an [AsyncIteratorObject](/docs/async-iterator-object) input or output are excluded and answer "Method not found". Procedures returning a `ReadableStream` fail with `-32603`.
- **No files.** `Blob`, `File`, and `FormData` cannot be sent in either direction: the link rejects them before sending, a procedure returning one fails with `-32603`, and the generator rejects file schemas.
- **A single input.** A procedure takes at most one positional param. A call with more, such as `{"jsonrpc":"2.0","method":"subtract","params":[42,23],"id":1}` from the JSON-RPC specification examples, fails with `-32602` "Invalid params: expected at most 1 positional parameter, received 2.", and such a notification is dropped without running the procedure. Send the input as one param instead: by-name `{"minuend":42,"subtrahend":23}`, `[{"minuend":42,"subtrahend":23}]`, or `[[42,23]]` for a tuple input. To call servers that take several positional params, use [`encodeParams`](/docs/openrpc/link#positional-params) on the link.
- **Request/response over HTTP only.** Server-to-client notifications, WebSocket transports, `GET`-encoded requests, and JSON-RPC 1.0 are not supported.
- **Plain JSON.** Types such as `Date` or `BigInt` arrive as strings. Restore them with the [Smart Coercion Plugin](/docs/openrpc/link#restoring-native-types).
- **Number ids** are read as JavaScript numbers, so integers beyond `Number.MAX_SAFE_INTEGER` lose precision. Use string ids for larger values.
